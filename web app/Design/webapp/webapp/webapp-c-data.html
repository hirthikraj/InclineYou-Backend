Data — six ways to show what the product knows

The choice between these is really one question: is the reader comparing, or reading? Comparing wants a table — aligned columns, sortable, selectable in bulk. Reading wants a list row, a stat or a timeline. Getting this backwards produces the two commonest failures in a business tool: a table nobody can scan, and a card list nobody can total.

SUPERSEDED · 23 Aug 2026 — the web app is ONLINE-ONLY

This page was written offline-first. That decision has been reversed for the web: the web app writes every response straight to the server — no browser storage, no write queue, no sync. Offline-first remains the architecture of the phone (app/) and of nothing else.

So wherever this page draws or argues for an offline banner, a synced / queued pill, a “held on this device” count, or the sync-queue screen, that chrome is not built on the web. The reasoning around it is kept, because the rest of each finding depends on it — only the offline half is void.

Authority: CLAUDE.md at the repo root, and web app/web/AGENTS.md. Do not re-derive the offline behaviour from this page.

List row

Stable

The left pane of a list–detail split. It is not a table row: there are no columns to compare, because the reader has already decided to look at one thing and the list only has to help them find it and keep their place.

Queue item

Stable

One unsent write, with why it is still waiting. On the phone this list is a lifeline — the gym has no signal. At a desk it is a monitor: same data, less urgency, and it moves from a hero screen to a system destination.
