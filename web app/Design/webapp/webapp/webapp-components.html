SUPERSEDED · 23 Aug 2026 — the web app is ONLINE-ONLY

This page was written offline-first. That decision has been reversed for the web: the web app writes every response straight to the server — no browser storage, no write queue, no sync. Offline-first remains the architecture of the phone (app/) and of nothing else.

So wherever this page draws or argues for an offline banner, a synced / queued pill, a “held on this device” count, or the sync-queue screen, that chrome is not built on the web. The reasoning around it is kept, because the rest of each finding depends on it — only the offline half is void.

Authority: CLAUDE.md at the repo root, and web app/web/AGENTS.md. Do not re-derive the offline behaviour from this page.

Component library — 43 components, one page each

Every component below is documented on its own, in the same order: definition, a specimen on a bench, anatomy with numbered callouts, variants, a full state matrix, specifications with token names, content rules, do and don’t pairs, accessibility, the class API, and when not to use it. The block order follows the Design System Doc Spec; the one-component-per-page rule follows Carbon and Atlassian rather than the everything-at-once gallery this library replaced.

What changed, and why

The first version of this put every control into a single 1440×900 frame inside a fake browser window. That is a gallery, and it answers exactly one question — does the density hold together. It cannot say what a component’s states are, what its anatomy is called, when to use it instead of the next one, or what its accessible name should be. Those are the questions a handoff actually gets asked, so each component now has a page, and the specimens sit on a neutral bench rather than inside a screenshot of a screen.

01How the pages are built

BlockAnswers
DefinitionWhat it is, in two sentences, plus the class, the counts and where it is used.
SpecimenThe component alone on a neutral bench with an 8px grid, so alignment is checkable. Not inside a fake browser window — that reviews a screen, not a component.
AnatomyNumbered pins sitting outside the specimen with leader lines, and a legend naming each part and its token.
VariantsEvery variant, labelled, with what each one means and what it must never be used for.
StatesA matrix: rest, hover, focus-visible, pressed, selected, disabled, error, read-only — whichever apply.
SpecificationsHeight, padding, radius, type, colour and target, each with its token name and a note. Several rows record a real bug this project shipped.
ContentLabel rules as yes/no pairs, where the words matter.
Do and don’tTwo live specimens side by side, each with the reason underneath. The wrong one is drawn, not described.
AccessibilityRole, accessible name, keyboard, focus, and measured contrast ratios.
APIThe class contract and the attributes the stylesheet reads.
When not to useThe situation, and the component to use instead — linked.

02What a component has to have before it is Stable

Two components are marked Beta here, and both for the same reason: they need a real interaction to judge, and one of them has an open accessibility question.

ComponentStatusWhat is outstanding
Command paletteBetaThe scoping rule — actions belong to the current match, not to a global list — is right on paper and needs a real index behind it to prove it stays fast at 873 exercises plus 22 clients.
Builder cellBetaMoving an exercise between days wants drag. Drag alone fails WCAG 2.2 SC 2.5.7, so the keyboard path (cut / move to… / paste) has to ship with it, not after. Until that is built this stays Beta.
