Getting in — and the eight questions after it

The page this replaces drew 4 frames and documented a six-step setup wizard. app/src/setup/draft.ts ships SETUP_STEPS and it is 8 — name, experience, specialities, certifications, languages, hours, packs, payment — and not one of the six was one of the eight. Not renamed: absent. The onboarding half of that file documented a flow somebody imagined, in the file whose only job is to document onboarding.

The sign-in half was closer and got the two things a sign-in screen must get right wrong. It promised the code would arrive on WhatsApp, which WHATSAPP_OTP_ENABLED = false refuses to send — the API function throws rather than falling back, precisely so a trainer is never told to check WhatsApp for a text. And it drew six separate inputs for the code, which is the one thing the mobile behaviour spec forbids by name: “one real input under six slots — never six inputs”. The justification given was backwards — autocomplete="one-time-code" targets one field, and six inputs are what break it.

So this is a rebuild: 15 frames covering the phone, the code and its 4 refusals, the second paths, which book, all 5 identity states, the 8-step flow, and the device list — which appears in no file in this set and which the mobile design calls the most dangerous interaction in the whole app. Every policy number is imported from application.yml and asserted, including an assertion that the mobile spec’s wrong-code row disagrees with it.

SUPERSEDED · 23 Aug 2026 — the web app is ONLINE-ONLY

This page was written offline-first. That decision has been reversed for the web: the web app writes every response straight to the server — no browser storage, no write queue, no sync. Offline-first remains the architecture of the phone (app/) and of nothing else.

So wherever this page draws or argues for an offline banner, a synced / queued pill, a “held on this device” count, or the sync-queue screen, that chrome is not built on the web. The reasoning around it is kept, because the rest of each finding depends on it — only the offline half is void.

Authority: CLAUDE.md at the repo root, and web app/web/AGENTS.md. Do not re-derive the offline behaviour from this page.

03Six inputs for the code, and the reason given was backwards

Defect

What is wrong

The old page drew six separate boxes and defended them: “Six separate inputs rather than one field, because a desk browser will happily autofill a six-digit code from a paired phone and a single field defeats that.” It is the other way round. autocomplete="one-time-code" is a hint on one input. 02Competitor analysis — four products, four passwords

Four products, and the survey produced a single sentence: not one of them can let a trainer in without an email address and a password. For a trainer standing in a gym in Adyar, the phone number is the identity and WhatsApp is the inbox — an email they check weekly is a worse credential than a number they answer in ten seconds. That is the whole of X REP’s front door, and it is the one part of this product where the category is not merely behind but pointed somewhere else.

Rows marked Verified trace to the vendor’s own help centre or sign-up page. Two help centres return 403 to a direct fetch; where a claim came from a search summary of such a page rather than the page itself, the row says so.

ABC Trainerize — and you cannot sign up in the app at all

Verified from vendor help centre

What they built

Leave this

Signing up in a browser only, and Timmy Explorer. The first says the phone is a client of the web, which is the opposite of this product — the phone is where the work happens and the desk is the second seat. The two rows that disagree

The mobile design’s behaviour spec says “Wrong-code limit: 5, then a 5-minute lock”. The server says 3 and 10, and api/auth.ts follows the server. So the design document is the copy that is wrong, and it is the copy every other file in this set has been reading — which is how a screen ends up promising two more attempts than a trainer has.

The rule this establishes for the set: where a policy number is enforced, the enforcing file is the source of truth, and a design document that states it is a comment. Both numbers here are imported from application.yml’s values and asserted, including an assertion that the two disagree — so the day somebody fixes the design doc, this page fails and gets updated with it.

And one number that is really three sentences

throttleMessage in the app does something worth copying exactly: it changes its wording with the magnitude of the wait, because the same sentence is a lie at two of the three scales. Under 90 seconds it says “That’s a lot of codes. Try again in 45 seconds.”; under 90 minutes it counts in minutes; past that it says “That’s too many codes for this number today. Try again in about 4 hours.” — because the ladder refuses for half a minute and the day’s ceiling of 10 refuses for hours, and “give it a minute” is a lie in the second case that the next attempt exposes.

Four refusals, four recoveries

The message slot

Two of these four are not the trainer’s fault, and one of those two is the reason this bench exists. An expired code is amber, not red. It is the clock’s doing, it spends no attempt, and styling it as an error is NN/g’s third hostile pattern — error treatment on a message that reports no error. The set’s own tokens make that easy and the old page threw the distinction away by having one state.

The app insists on the code field for exactly this, and falls back to the status only for a proxy that strips the body.

06When the SMS does not arrive

There is no credible published OTP delivery figure for India — every “99.9%” is vendor marketing. Vendor material in 2026 puts transactional SMS at 92–98%, which is another way of writing a 2–8% hard-fail tail, and the honest latency assumption is 5–15s at p50 and 30–60s+ at p95. So the code can never be the only path, and the resend button can never be the only recovery.

12Devices — the most dangerous interaction in the product

This screen lives in Settings and belongs to this document, because it is the other half of signing in — and because the mobile design opens its section on it with the strongest sentence in either file: “This is the most dangerous interaction in the whole app and it is invisible on a screen.”

The failure it exists to prevent

A trainer logs a full session in a basement with no signal. That evening they sign in on a new phone. If signing in on the new device revokes the old session, the old phone hits a 401, a naive logout handler wipes local storage — and an entire session’s sets are gone, silently, with no error the trainer ever sees. Nothing on any screen in this set would have shown it, which is exactly why it needed writing down.

THE RULE THAT PROTECTS A SESSION

Never wipe local data on a 401.

Token revocation is a sync-permission event, not a data-lifecycle event. A trainer logs a full session in a basement with no signal, signs in on a new phone that evening, and a naive logout handler on the old one turns a 401 into an erased session. Quarantine the outbox and show it — never delete it.

AND WHY THE LIST IS LONG

Concurrent sessions are allowed on purpose.

A single-session login would be actively harmful here: the phone on the floor and the browser at the desk are both real, at the same time, every day. New-device sign-in completes normally and the others get told out of band — an interstitial is reserved for a new device in a new country.

Four rules, and all four are the opposite of the obvious implementation. Never wipe local data on a 401 — token revocation is a sync-permission event, not a data-lifecycle event, so the outbox is quarantined and shown, never deleted. Allow concurrent sessions — single-session logins are actively harmful here, because the phone on the floor and the browser at the desk are both real at the same time, every day; OWASP leaves this to the application and the old “no duplicate sessions” ASVS rule was Level 3 and was dropped. Notify, don’t interrupt — a new sign-in completes normally and the other devices get told out of band; an interstitial is reserved for a new device and a new country. Drain before you revoke — the confirm counts what is still upstream and pushes it first.

And the confirm refuses rather than proceeds. 4 things on that phone have not reached the server; if the push fails, the sign-out does not happen. Sign-out is the one moment a trainer can genuinely lose a session’s work, and a dialog that says “4 workouts still to upload from that phone” is the difference between an informed decision and a silent discard.

The web makes this worse, not better, and that is the argument for the screen. The browser is a third device and the one most likely to be shared — a gym’s front-desk PC is exactly the machine somebody signs into once and never signs out of. The list names the device, the city and the last activity, because those three are enough to recognise yourself or not; the six-day-idle row carries a warning because six days idle on a shared machine is the case worth flagging.

What is not here: a force-update wall. The phone needs one — a server floor plus a screen, with a support route on it, because a wall with exactly one button and no escape is what gets an iOS build rejected under Guideline 2.1. A browser reloads to the current build by definition, so the whole section deletes on the web. Its true web analogue is a stale tab left open across a deploy, and that is §16’s.

Heuristic 5, error prevention, argues that the ₹1 self-transfer is not enough. That is honest, and it is not the same as safe: until a lookup exists, this is the one field in the whole product where a typo costs money, and it is §16’s first row.

/settings/devicespageThe other half of signing in. In Settings because that is where a trainer looks for it; in this document because §12.

What has no route, on purpose. There is no /forgot-password, no /reset and no /change-password, because there is no password — and every competitor in §02 ships all three plus the support load that comes with them. There is no /logout either: signing out is a consequential action with a confirm, and §12 is why. And there is no force-update wall, because a browser reloads to the current build by definition.

16Still open

7 things, and none of them blocks any more. The two that did were about money and about getting in at all — the correct pair for this file to have been blocked on — and neither was waiting on a decision this document could make. What closed them was narrowing the claim: one moved the risk to where the money actually moves, the other stopped shipping a fallback that turned itself off. Both are still work; neither now stops a component being called Stable.

OpenKind Why it is still open
A UPI typo costs moneyOpenDe-blocked, not solved. A name lookup still needs a provider nobody has wired, and no amount of design substitutes for one. What changed is that the field stopped being where the risk lives. Two decisions: the handles are pickable and the local part defaults to the trainer’s own number — in India the common shape is <phone>@<psp>, and the phone is the one string this product has just verified by sending a code to it — and the read-back happens again at the first collection, with the amount beside it. A wrong ID caught before a ₹9,600 collect is an edit; caught after, it is somebody else’s money. Setup is not where the money moves, so setup is not where this has to be safe. One prerequisite, named: SignInSession does not carry the verified number, so it has to reach the setup flow before that default can be filled in.
Every second path into the productOpenDe-blocked by refusing to ship a dark one. WhatsApp needs a BSP and voice needs a channel that does not exist; neither is a design decision, so the honest count of fallbacks that can exist this quarter is one — the human route. Its defect was not that it was missing but that it switched itself off: SUPPORT_WHATSAPP_NUMBER reads an env var defaulting to empty, and the lock screen rendered a disabled button when the var was absent. A fallback that silently disables itself is indistinguishable from a product that never had one, and worse, because it occupies the space the real recovery should be in. Changed in OtpScreen: the row is not drawn when it cannot work, and the sentence underneath carries what is always true — the lock is on the number and not the account, it lifts by itself, and another device is unaffected. Voice OTP stays on this list as work, not as a blocker.
The country pickerOpenThe mobile design has one (7c) with a searchable sheet and 56px rows, because NRI clients and Gulf-based trainers are real. Every frame here is +91 with a chevron that opens nothing. The server’s regex is ^[6-9]\d{9}$ — India only — so drawing a picker before the backend accepts anything else would be the same defect as the WhatsApp button.
A stale tab across a deployOpenThe phone’s force-update wall deletes on the web, but its cause does not: a browser left open for a week against an API that has moved on. The honest analogue is a banner that says the build is old and reloads on click — never a wall, because the tab may hold an unsaved draft. Not drawn.
Sign-in with something already queuedOpenA trainer signs in on a browser that has unsynced work from a previous session on the same machine — a shared front-desk PC where two trainers alternate. Whose outbox is it? The phone cannot produce this case and the web can. Not answered.
The invite link's lifetimeOpen/invite/:token arrives by WhatsApp and WhatsApp links live forever in a chat. The token opens no data, so the exposure is a trainer’s name — but an expiry and a used-once rule are still owed, and neither is specified on either half.
Two drafts, one flowOpenSetup answers live in expo-secure-store on the phone and would live in the browser here. A trainer who starts on one and finishes on the other has two partial drafts and the server sees only the finished one. Frame 4b states the rule it assumes — whichever finishes first wins — and nothing enforces it.
