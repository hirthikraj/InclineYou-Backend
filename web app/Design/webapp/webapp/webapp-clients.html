Clients — the roster, the file, and the three ways out

The page this replaces drew 5 frames and, in three places, described a product that is not there. It documented a client file with six tabs — FILE_TABS is 4, and §14 of the mobile design makes it a rule with a reason. It documented intake as “six fields either way” — AddClientScreen’s docstring is titled two fields, and intake is a 4-step flow whose second step creates the record. And it put “top set · bench 65 kg” among the four numbers the trainer actually acts on; buildOverview returns five rows and not one of them is a top set.

The rebuild imports the two modules that decide everything on this screen — clients/roster.ts and clients/file.ts — and running the same trainer’s data through both of them produced the thing this page opened on. roster.ts promises that “‘needs attention’ means one thing in this app, not two”. On 11 Aug it meant two: Today named 6 clients and the roster named 9, they agreed about 4, two of those four were in a different order, and one client’s empty pack was red here and amber there with a different sentence on each. That is fixed. The model is now one exported band table in deck.ts that the roster imports whole — §02 — and this generator asserts the two screens agree on weight, severity, wording and order for every one of the 6 clients they share.

So: 17 frames — the roster as a real table with the severity spine and one inline verb per row, its five states, the search dead end, all 4 tabs of the file plus body metrics, all 4 intake steps including the gate nobody has drawn, and pause / archive / remove, which is the one real delete in the product and appears in no file in this set. Every figure, count, rupee and rank below is derived and asserted, including 9 corrections owed to other documents and 8 defects in the app itself that only turned up because the screens were drawn against the code rather than against the page before them.

02Two modules, one phrase, two lists

roster.ts opens with a promise: “the thresholds are imported from the deck rather than restated, because the whole point of the severity spine being the same 2px bar on both screens is that ‘needs attention’ means one thing in this app, not two.” The thresholds were imported. Nothing else was. This page imports gen_today, which ports buildAttention from home/deck.ts, and running the same trainer’s data through both modules on the same morning is what found it: Today named 6 clients, the roster named 9, and they agreed about 4.

Four separate disagreements, and none of them cosmetic.

Two weight scalesThe deck weighed overdue money at 2000 + days, the roster at 4000 + the rupees owed. So the same client sorted differently on two screens, and of the 4 both lists carried, Priya N and Kavya M swapped places.
Raw weights, so the tiers leakedWorse than a second scale. 4000 + owed is unbounded, so any debt over ₹1,000 outranked unavailable — the band whose own comment in that file read “ranked ABOVE money, which nothing else here is, and deliberately”. The comment had been false since the first client owed four figures.
Two answers about moneyThe deck raised a row for any due payment; the roster raised one only past 7 days. Two clients owing ₹9,000 and ₹3,000 were on Today and absent from the roster’s attention list — and the roster’s three-figure strip then said ₹6,000 owed beside a rail badge reading 3 and a money book reading ₹18,000.
Two words for one packAn empty pack was “Pack is empty” and critical here, “Pack finished” and alert there. Same package, two sentences and two colours, so the client was red on Today and amber on Clients and a trainer reading both had no way to know it was one fact.

The resolution: bands, in one file

Both rules about money were defensible and both words for a pack were readable. What was not defensible was two of each, so the model moved into deck.ts as one exported table — ATTENTION_BANDS, their order, their severities and the strings — and clients/roster.ts imports all of it. The division of labour is now explicit in both files: the deck owns the model, each screen owns its own selection. A screen may decline to raise a band; no screen may re-rank or re-word one it does show.

A band is worth 1000 and the magnitude inside it is clamped to 0–999, which is the part that fixes the leak: an amount orders rows within a band and can never lift one out of it. At ten lakh owed, due-soon still scores 2999 and pack-ending still starts at 3000.

04What a table is for

NN/g’s data-table article (Laubheimer, 2022) names four user tasks: find records that fit criteria, compare data, view or edit one row, act on records. A roster is all four, in that order of frequency, and every decision below serves one of them. The app is a card list because a phone reads one row at a time; the desk job is the second task, and a card list cannot do it.

The verbactOne button, always visible.

One action, always visible

NN/g is specific about this and it happens to fit the app exactly: inline row actions work “if you just have one or two”, and “inline actions should be visible at all times rather than showing on-hover”. attention.action is singular by construction — one row, one verb, because the row was ranked to produce it — so the table gets a real button in the last column and the other six verbs live behind the kebab. A hover-revealed action would fail the same guideline and be invisible to a keyboard.

The verbs, and where each one goes:

KindVerbWhat it does

And a seventh row state that is not a verb: Queued. A client written on this computer and not yet pushed shows its state instead of an action against it, which is Trailing’s first branch and the right order — a verb on a row the server has never seen is an invitation to act twice.

Selection does not move the rows
