Information architecture — what the web app is, and what it refuses to be

The app covers 62 use cases across eleven screens on a 390 px canvas. This document maps every one of them onto a 1440 px canvas and records what happened on the way: 22 unchanged, 17 reshaped, 10 promoted into something the phone could not do, 8 merged away, 3 deleted because they only existed to work around a phone, and 2 that exist only here. A port is a list of screens. This is a list of decisions.

SUPERSEDED · 23 Aug 2026 — the web app is ONLINE-ONLY

This page was written offline-first. That decision has been reversed for the web: the web app writes every response straight to the server — no browser storage, no write queue, no sync. Offline-first remains the architecture of the phone (app/) and of nothing else.

So wherever this page draws or argues for an offline banner, a synced / queued pill, a “held on this device” count, or the sync-queue screen, that chrome is not built on the web. The reasoning around it is kept, because the rest of each finding depends on it — only the offline half is void.

Authority: CLAUDE.md at the repo root, and web app/web/AGENTS.md. Do not re-derive the offline behaviour from this page.

01Three things change, and nothing else

Every colour, radius and spacing token is copied verbatim from trainx-design-system.html v1.2. If a value differs there, it is a bug here. What a bigger screen and a mouse actually change is exactly three things, and each one is measured rather than asserted:

DENSITY

The row goes 56 px → 44 px, the control floor 48 → 32.

WCAG 2.2 SC 2.5.8 asks for 24×24 CSS px for a pointer target. 32 clears it with margin. Anything plausibly touched on a convertible keeps 40.

NAVIGATION

Bottom nav + drawer → one 248 px rail, eleven destinations.

The split existed because a phone bar holds four. The drawer is deleted, not ported — a whole screen removed rather than translated.

INPUT

A keyboard exists: ⌘K, arrow-navigable lists, Escape, Tab-to-commit.

Leaving this out is the most common way a ported mobile design feels wrong on a desktop even when every pixel is right.

02The map

Four groups, eleven destinations, three routes outside the rail. Every destination is one click from every other at any moment — which is the single structural difference between this and the app, where seven of the eleven live behind a drawer.

03Routes

A web app that cannot be linked into is a phone app in a window. Every view below is addressable, survives a refresh, and answers the back button. The rule that decides the edge cases: a panel is a place and gets a URL; a selection is a mood and does not.

06Eight rules that settle the arguments

Written down because each one has a plausible opposite, and a design system that has not chosen between them produces two of everything.

01
A bottom sheet becomes a right panel when the thing behind it matters, and a modal when it does not.
Payments, sessions and add-client are panels — you decide them by looking at the ledger, the week or the roster. Archive is a modal, because nothing behind it helps and it must be answered.
02
Every panel has a URL. No selection does.
A panel is a place; a selection is a mood. /money/pay/anu can be pasted into a message. “These three rows are ticked” cannot, and pretending otherwise breaks the back button.
03
Filters and sorts live in the query string.
A trainer’s “who owes me money” view is ?status=active&sort=-owed. Making it addressable costs one line and turns a view into a bookmark.
04
The primary action sits in the page header, right-aligned. There is no floating button.
A FAB answers “what is reachable by a thumb”. On a 1440px canvas nothing is unreachable, so the button goes where the eye already is after reading the title.
05
Anything a list can do to one row, it can do to many.
Nudge, mark paid, reschedule, export, archive. If an action cannot be bulked it is worth asking why it is in a list at all.
06
Destructive actions are never the only thing a click can hit.
Archive and write-off live behind an overflow menu, take a confirm that names what will happen, and are reversible for ten seconds afterwards. The mobile rule, unchanged.
07
Escape closes exactly one layer.
Panel, then palette, then nothing. A single Escape that closes three layers is the fastest way to lose typed work, and the most common web-app bug in this category.
08
The rail never scrolls out of view, and never moves.
Eleven destinations, four groups, the same eleven at every width above 1024px. Navigation you can see is not navigation you have to open.

07Widths

WidthWhat happens
≥ 1600pxThe 1440 design holds; the right panel becomes a persistent third column on Clients and Money instead of an overlay. Nothing is stretched — tables gain breathing room, not columns.
1280 – 1599pxThe design width. The rail stays 248px, the list pane relaxes from 400px to 340px, and the week grid keeps all seven days.
1024 – 1279pxThe rail collapses to a 64px icon rail (.app--rail-min) with labels on hover; the list-detail split becomes single-pane with a back affordance. This is a laptop, so the 40px touch floor applies.
< 1024pxHand over to the app layout. A third design is not built. The mobile screens already solve this width properly, and a squeezed desktop table is worse than a phone list at every width below a tablet.

The decision worth arguing with

Below 1024 px this design stops and the app layout takes over. The alternative — one set of screens that flexes from 390 to 1600 — sounds cheaper and is not: the roster is a table here and a card list there, the calendar is a grid here and a day list there, and the workout console inverts its whole premise. Those are different designs wearing the same stylesheet.

08What is deliberately not here

Not builtWhy not
Body-metric photosThe capture flow is a camera flow. The web shows the photos and lets one be uploaded; it does not pretend to take one.
Push notificationsA desktop browser asks for permission in a way that most trainers will decline, and a declined permission is worse than none. Reminders go out over WhatsApp and email, which is what the app does anyway.
A tablet layoutDeliberate. Two layouts, honestly built, beat three that are each 80% right.
A light-theme frame setEvery token has a light pair and the toggle in the header proves it, but the twelve files are drawn dark. Drawing both doubles the surface area and halves the care per frame.
Live logging as the primary web jobThe console exists for review and repair. A trainer logging live is holding a phone, and designing the web as if they were not would be the single biggest misread available here.

09Open — three things I had to guess

DRAG AND DROP

Is dragging an exercise between days in the builder worth the accessibility cost?

Guessed yes, with a keyboard equivalent (cut / move / paste on the row menu). Drag alone would fail WCAG 2.2 SC 2.5.7.

THE UPI DEAD END

Does a trainer collecting on a desktop want a QR, a copyable link, or both?

Guessed both, QR first. A client sitting across the desk scans; a remote client gets the link pasted into WhatsApp.

WHO OPENS THIS

Is the web app for the 1st-of-the-month admin hour, or for daily use?

Designed for the admin hour: bulk actions, the ledger, exports and adherence lead. If it is daily, Today and Schedule need more depth than they have.
