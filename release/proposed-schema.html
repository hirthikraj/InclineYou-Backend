Conventions that hold on every table
primary-key
Every table has id uuid PRIMARY KEY DEFAULT gen_random_uuid(). Ids are normally generated client-side (UUID v4); the default is a fallback.
ownership
Trainer-scoped tables carry trainer_id and every query filters on it, so a wrong id answers 404, not 403.
soft-delete
deleted_at NULL means alive. Nothing is hard-deleted; every read filters deleted_at IS NULL. Log tables (otp_request, client_assignment, team_activity) have no deleted_at — a mistake is corrected by writing another row. Since V21 the request role holds no DELETE except on attention_dismissal, web_session and otp_request, and no UPDATE on the three logs.
erasure
Deleting an account is an erasure (P2), not a soft delete. erase_account() sets the personal columns of app_user, trainer and client to NULL under a CHECK that lists them, and deletes the trainer's trainer_business row and each erased client's client_schedule row with its slots, which are personal from end to end, so the rows stay as tombstones, and the phone number is released. It also deletes the person's web_session rows and empties billing_event.payload on their subscription; otp_request rows age out on their own 30 days, never early, because a running lock is an abuse control. A trainer deleting one client is the same erasure at client scale: erase_client(id), granted to the request role and refused unless the caller coaches that client, runs erase_clients() and writes an erasure_log row of kind client; the ledger stays as a nameless former client. purge_tenant() is the one hard delete: it empties a closed workspace once purge_after has passed. What survives is erasure_log, which holds counts only, and nameless amounts and dates in workspaces the person did not own.
updated-at
updated_at is maintained by the set_updated_at() trigger on every table that has it, and is the sync cursor. Since V21 there is no exception: working_hours, time_block and batch used to take the device's own value on sync push, which a wrong clock turned into an edit no other device ever pulled.
tenant-id
tenant_id is the workspace a row belongs to. It is stamped on insert by stamp_tenant_id(), refused any change by freeze_tenant_id(), and row-level security filters on it.
money
Money is numeric(10,2), percentages numeric(5,2). One currency per workspace: tenant.currency (ISO 4217, default INR) is the only currency that workspace's money rows may carry. Each one has a composite foreign key (tenant_id, currency) → tenant(id, currency), so no SUM ever adds two currencies, and a workspace's currency cannot change once a money row points at it. Only currencies with at most two decimal places are offered (Currency.getDefaultFractionDigits() ≤ 2, checked in code); the three-decimal Kuwaiti and Bahraini dinars and the Omani rial are refused rather than rounded. The one exception is subscription, whose price and currency come from its plan_price row — the price of the trainer's billing region — not from a workspace.
phone
Every phone column is E.164 (+919841022119), varchar(16), under the same format CHECK: + and 7–15 digits, and a +91 number must still be a ten-digit Indian mobile. One column, never a country code and a number split in two. Parsing, validation and display go through libphonenumber on the backend and the web; a number typed without + is read in the region of the workspace's tenant.country. The display grouping and the wa.me link (the digits after +) are derived, never stored.
time
An instant is timestamptz, always UTC. A date or a wall-clock time is a calendar day or a time in the trainer's timezone (trainer.timezone, IANA), never the server's and never the client's — one diary has one clock. client.timezone only converts what the client is shown.
enumerations
Enumerated columns are plain varchar, never a Postgres ENUM. Vocabularies (profile lists, nudge kinds, payment.method) are validated in application code; since V21 state machines and money columns also carry a CHECK, so a new state is a code change plus one DROP / ADD CONSTRAINT in a migration. Legal values are listed per column under allowedValues.
foreign-keys
Unless stated otherwise a foreign key is ON UPDATE NO ACTION, ON DELETE NO ACTION — rows are soft-deleted, so nothing cascades.

One client's session in the trainer's diary: who, when, for how long, and what happened. Every screen that asks when is this trainer busy reads this table — the day and week views, Today, the clash warning on Book, a free gap, a client's next session — so it is shaped for one read above all: this trainer's live sessions between two instants, answered by one index range scan that never visits the table. Overlap is allowed and named, never refused: a floor trainer's 06:00 carries four clients on purpose, and Book says "Arjun S is already here" and then books anyway. So the database refuses only what is always wrong — one client booked twice at the same start — and makes every other clash a cheap read. Two clients at one time are two rows, so the pack, the no-show and the undo stay per person. Rows are laid down from the client's standing week (client_schedule_slot) or booked by hand. One row from booking to log: the same row is booked, opened on the gym floor (started_at), finished (ended_at, status = done), and its logged exercises and sets hang off it; a walk-in logged with no booking is a row created done. It trains one workout, whose exercises and sets pre-fill the log. Backend and web; not in sync for v1. Row-level security: the staff tier (scheduled_session_tenant); the portal's scheduled_session_client policy returns with the portal.

What changed in review (25 Sep 2026)
  • workout_session is merged in. A booked session and its log were two rows joined by workout_session.scheduled_session_id, so mark done wrote both, and a session could be done in the diary with no log or logged with no diary row. One row now: started_at and ended_at come across; session_date goes (it is scheduled_at in trainer.timezone); logged_by is held for the portal, since in v1 only the trainer logs. The logging tables will point here.
  • workout_id replaces program_id, template_day and day_label → workout. A session trains one workout; its program, week, day and name are read from it, so they cannot disagree, and opening the log is one key to the exercises and sets it pre-fills from. NULL = nothing planned: the log opens empty.
  • The end is stored. ends_at timestamptz NOT NULL, kept by set_session_ends_at() from scheduled_at + duration_minutes. Two sessions clash when a.start < b.end AND a.end > b.start; without a stored end every clash and free-gap read computed it per row from a nullable duration and could not use an index for it. A trigger rather than a generated column because timestamptz + interval is STABLE in Postgres (a day's length depends on the zone), and a generated column refuses anything that is not IMMUTABLE.
  • duration_minutes is NOT NULL, 1–480, smallint (was a nullable integer). NULL meant "the client's default", so changing that default later silently moved the end of sessions already booked — and a session with no known end cannot be checked for a clash. The 480-minute cap is also what keeps the clash read a plain btree range: no session starts more than eight hours before one it overlaps.
  • from_schedule becomes slot_id → client_schedule_slot: which standing slot laid this row down. NULL = booked or moved by hand, the flag's own rule, but now naming the slot — so editing Tuesday's slot touches Tuesday's future rows and nothing else, and the reconcile stops matching rows to the week by exact instant. A double-clicked Book (the id is minted on the server) or a reconcile racing a hand booking wrote two rows; the second now answers 409, which the web already words as "something else has that slot". A cancelled session gives its instant back, so it can be rebooked.
  • Indexes rebuilt around three reads — the diary, one client's sessions, and the double-booking guard. Dropped: idx_scheduled_session_trainer_id and _scheduled_at (nothing reads sessions across trainers by time; a reminder sweep, when it exists, gets its own partial index), _delivery_mode (nothing filters on it — the chips count inside a day already read), _client_id (replaced by (client_id, scheduled_at)), and _series / _batch with their held columns.

CREATE FUNCTION set_session_ends_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.ends_at := NEW.scheduled_at + make_interval(mins => NEW.duration_minutes);
  RETURN NEW;
END $$;

set_logRLS

One set of a session_exercise: what the plan asked and what was done, in the same terms, side by side, for good. A set is described once by two kinds — how the load is measured (load_kind) and what the set asks for (effort_kind) — and then carries a target value and an actual value for each. When the log opens every prescribed workout_set is copied in, targets filled and actuals empty, in the same INSERT…SELECT that copies the exercises. Logging a set is one UPDATE of a row already there, pre-filled from its target, so the common case is one tap on done; an extra set is one INSERT. Opening the log is one read of this table, with no join back to the plan. Row-level security: the staff tier (set_log_tenant); the portal's client policy returns with the portal.

What changed in review (25 Sep 2026)
  • Actuals are in the target's own terms (decided 25 Sep 2026): load_value and effort_value replace load_kg, reps, duration_seconds and distance_m. Four fixed-unit columns could not say a machine level or tell a timed set from a rep set without guessing; two values read through two kinds can, and target and actual line up one to one. The unit of each is set by its kind (table below).
  • The kinds are shared, and required: load_kind and effort_kind describe both the target and the actual, copied from the plan's set when the log opens. An extra set takes the kinds of the set before it.
  • Targets are copied, not referenced: target_load_value, target_effort_value, rest_seconds, tempo. A foreign key to workout_set would lose every past target when a workout is edited, because editing rewrites its set rows.
  • Rows are laid down when the log opens. A skipped set is a real row with done_at NULL; planned tells a prescribed set from an extra one (a planned bodyweight set to failure has no target values at all, so their absence cannot be the signal); the planned count is a count of planned rows, so session_exercise.planned_sets is dropped.
  • Swapping to an alternative replaces that exercise's not-done set rows with the alternative's prescribed sets; done sets stay as logged. set_number → position 1–50; RPE 1–10 in half steps; no deleted_at — a mistaken extra set is deleted.

The log, as queries

 
-- opening the log: lay down every prescribed set with its kinds and targets
INSERT INTO set_log (session_exercise_id, position, planned, load_kind, effort_kind,
                     target_load_value, target_effort_value, rest_seconds, tempo)
SELECT sx.id, ws.position, true, ws.load_kind, ws.effort_kind, ws.load_value, ws.effort_value, ws.rest_seconds, ws.tempo
FROM   session_exercise sx JOIN workout_set ws ON ws.workout_exercise_id = sx.planned_from
WHERE  sx.session_id = :session;

-- logging a set: one tap, pre-filled from the target
UPDATE set_log SET load_value = :load, effort_value = :effort, rpe = :rpe, done_at = now() WHERE id = :set;

-- an extra set: the kinds of the set before it
INSERT INTO set_log (id, session_exercise_id, position, planned, load_kind, effort_kind, load_value, effort_value, done_at)
SELECT :id, :sx, position + 1, false, load_kind, effort_kind, :load, :effort, now()
FROM   set_log WHERE session_exercise_id = :sx ORDER BY position DESC LIMIT 1;

-- planned 3, did 2 of them, plus 1 extra
SELECT count(*) FILTER (WHERE planned)                         AS planned,
       count(*) FILTER (WHERE planned AND done_at IS NOT NULL) AS done_of_planned,
       count(*) FILTER (WHERE NOT planned)                     AS extra
FROM   set_log WHERE session_exercise_id = :sx;

Its terms — name, service, basis, amount, discount_amount, the trainer share, currency and start_date — can be corrected until the first payment is collected and are frozen after (freeze_package_terms()); a different deal is a new package. What legitimately changes mid-way — the session counts, the end date, a pause, the due date — changes only by a row in package_adjustment, which applies itself here; a direct UPDATE of those columns is refused (guard_package_balance()) — and the debt by a write-off, which is a payment row. What is still due is amount − Σ paid − Σ written off over its payment rows, computed on every read and stored nowhere.

What changed in review (25 Sep 2026)
  • Each client buys only their own kind of pack (decided 25 Sep 2026): check_package_client_type() refuses a gym client a trainer's pack, an independent client a gym pack, and a pack-less gym sale with no trainer share. Was checked in code only. So a gym client's packages are always gym, floor packages.
  • A refunded package is final (decided 25 Sep 2026).
  • The balance and the dates move only through the log (decided 25 Sep 2026): guard_package_balance() refuses a direct change to sessions_total, sessions_remaining, end_date, paused_at and paused_days once the package has any package_adjustment row — until then it is still the sale and can be corrected — and to due_date always after the sale. Only apply_package_adjustment() may write them.
  • refunded is real now (decided 25 Sep 2026): a fully paid package is closed by a refund row in payment. package_closed ties closed_at to every closed status.
  • A write-off is a payment row (decided 25 Sep 2026): written_off_at and written_off_amount are dropped. Writing a package off inserts a payment with status = 'write_off' for what is forgiven, so it sits in the package's payments list with the rest of its money, and paid, written off and still due are all sums over one table. The stored total could disagree with the rows it was summed from; a sum cannot.
  • name added, copied from the pack at sale (decided 25 Sep 2026). The client file used to join back to the pack for it, so renaming a pack renamed every package sold from it, and a package sold without one had no name.
  • The deal is frozen once money is collected (decided 25 Sep 2026): freeze_package_terms() refuses a change to name, service, basis, amount, discount_amount, the trainer share, currency and start_date while a paid, written-off or refund payment points at the package — a re-priced package would leave its settled rows adding up to the wrong total. Before it, a half-paid package could be re-priced and its paid rows would no longer add up to it. sessions_total, end_date and sessions_remaining are not in the list: they move mid-way, and only through their package_adjustment actions (in code).
  • gym_share_percent → trainer_share_percent / trainer_share_amount, copied from the pack at sale (decided 25 Sep 2026).
  • service added, copied from the pack at sale, and type → basis — the pack's two new facts, frozen on the sale (decided 25 Sep 2026).
  • Sessions are charged to the matching service: a client with a floor pack and a remote pack has each used by its own sessions (idx_package_charge). A session with no live package of its service is done and uncharged — the log says so, and the dues list offers the sale.
  • package_basis replaces package_type + package_sessions_nonnegative, and adds sessions_remaining ≤ sessions_total. package_trainer_share: at most one of the two share columns, the amount no more than the package, and only on a floor sale.

CREATE FUNCTION freeze_package_terms() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF (NEW.name, NEW.service, NEW.basis, NEW.amount, NEW.discount_amount, NEW.trainer_share_percent,
      NEW.trainer_share_amount, NEW.currency, NEW.start_date)
     IS DISTINCT FROM
     (OLD.name, OLD.service, OLD.basis, OLD.amount, OLD.discount_amount, OLD.trainer_share_percent,

      USING ERRCODE = 'check_violation';
  END IF;
  RETURN NEW;
END $$;

CREATE FUNCTION guard_package_balance() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF coalesce(current_setting('inclineyou.package_adjusting', true), 'off') = 'on' THEN RETURN NEW; END IF;
  IF NEW.due_date IS DISTINCT FROM OLD.due_date
     OR ((NEW.sessions_total, NEW.sessions_remaining, NEW.end_date, NEW.paused_at, NEW.paused_days)

BEGIN

END $$;

The history of a sold package: every change to its sessions, its dates and its due date, one row each, oldest first — pause, resume, extend, a session-count correction, a due-date move, and each session it is charged for. The package holds the current state; this table is how it got there, and the two cannot disagree because writing a row here is the change: apply_package_adjustment() applies each row to the package in the same statement, and the package refuses those columns from anywhere else (guard_package_balance()). So 12 bought · 7 trained · 1 given back · 4 left, ends 18 Dec, due 15 Oct always shows its working. Append-only: the only write after an insert is reversed_at on a charge, once. Money is not here — paid, written off and refunded are payment rows. Row-level security: the staff tier (package_adjustment_tenant). Backend and web; not in sync for v1.

What changed in review (25 Sep 2026)

The service writes one row and nothing else, so no code path can update one side and forget the other. It also refuses what makes no sense — pausing twice, resuming what is not paused, extending a pack that never expires, charging a paused pack, changing a closed one.
  • A resume's length is measured from the pause's start, never typed.
  • Due-date moves are logged (decided 25 Sep 2026): kind due_date, with due_date and previous_due_date.
  • A session's charge lives here (moved out of scheduled_session, agreed 25 Sep 2026): new kind session, with session_id and sessions = −1. Mark done is one transaction — the session UPDATE, this INSERT, and package.sessions_remaining − 1. Undo sets reversed_at and gives the session back; the charge is reversed, never deleted or overwritten, so the log keeps both facts. A redo is a new row.

CREATE FUNCTION package_adjustment_append_only() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF OLD.reversed_at IS NULL AND NEW.reversed_at IS NOT NULL
     AND (to_jsonb(NEW) - 'reversed_at') = (to_jsonb(OLD) - 'reversed_at') THEN
    RETURN NEW;                                   -- undoing a session charge, once
  END IF;
  RAISE EXCEPTION 'package_adjustment is append-only: only a session charge''s reversed_at may be set, once'
    USING ERRCODE = 'check_violation';
END $$;

CREATE FUNCTION apply_package_adjustment() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE pkg package%ROWTYPE; tz text;
BEGIN
  SELECT * INTO pkg FROM package WHERE id = NEW.package_id FOR UPDATE;
  IF TG_OP = 'UPDATE' THEN                                     -- the one update append-only allows: undoing a charge
    PERFORM set_config('inclineyou.package_adjusting', 'on', true);
    UPDATE package SET sessions_remaining = sessions_remaining + 1 WHERE id = pkg.id;
    PERFORM set_config('inclineyou.package_adjusting', 'off', true);
    RETURN NEW;
  END IF;
  IF NEW.kind <> 'due_date' AND pkg.status <> 'active' THEN
    RAISE EXCEPTION 'package % is %: only a running package can be %', pkg.id, pkg.status, NEW.kind USING ERRCODE = 'check_violation';
  END IF;
  CASE NEW.kind
  WHEN 'pause' THEN
    IF pkg.paused_at IS NOT NULL THEN RAISE EXCEPTION 'package % is already paused', pkg.id USING ERRCODE = 'check_violation'; END IF;
    pkg.paused_at := NEW.effective_at;
  WHEN 'resume' THEN                                           -- the pause's length is measured, never typed
    IF pkg.paused_at IS NULL THEN RAISE EXCEPTION 'package % is not paused', pkg.id USING ERRCODE = 'check_violation'; END IF;
    SELECT timezone INTO tz FROM trainer WHERE id = pkg.trainer_id;
    NEW.days := greatest(0, (NEW.effective_at AT TIME ZONE tz)::date - (pkg.paused_at AT TIME ZONE tz)::date);
    pkg.paused_at := NULL;
    pkg.paused_days := pkg.paused_days + NEW.days;
    pkg.end_date := pkg.end_date + NEW.days;                   -- no expiry stays no expiry
  WHEN 'extend' THEN
    IF pkg.end_date IS NULL THEN RAISE EXCEPTION 'package % never expires: there is nothing to extend', pkg.id USING ERRCODE = 'check_violation'; END IF;
    pkg.end_date := pkg.end_date + NEW.days;
  WHEN 'sessions' THEN                                         -- package_basis refuses a count below what is used
    pkg.sessions_total := pkg.sessions_total + NEW.sessions;
    pkg.sessions_remaining := pkg.sessions_remaining + NEW.sessions;
  WHEN 'session' THEN                                          -- and refuses a charge with nothing left
    IF pkg.paused_at IS NOT NULL THEN RAISE EXCEPTION 'package % is paused: a paused package is not charged', pkg.id USING ERRCODE = 'check_violation'; END IF;
    pkg.sessions_remaining := pkg.sessions_remaining - 1;
  WHEN 'due_date' THEN
    NEW.previous_due_date := pkg.due_date;
    pkg.due_date := NEW.due_date;
  END CASE;
  PERFORM set_config('inclineyou.package_adjusting', 'on', true);
  UPDATE package SET sessions_total = pkg.sessions_total, sessions_remaining = pkg.sessions_remaining, end_date = pkg.end_date,
                     due_date = pkg.due_date, paused_at = pkg.paused_at, paused_days = pkg.paused_days
  WHERE id = pkg.id;
  PERFORM set_config('inclineyou.package_adjusting', 'off', true);
  RETURN NEW;
END $$;
CREATE TRIGGER trg_package_adjustment_apply BEFORE INSERT OR UPDATE OF reversed_at ON package_adjustment
  FOR EACH ROW EXECUTE FUNCTION apply_package_adjustment();   -- fires after _append_only, by name

Who collects is fixed by the client (decided 25 Sep 2026): an independent client pays the trainer — UPI to the trainer's own VPA, cash, or a bank transfer — and a gym client pays the gym's reception, whose method we do not record. What changed in review (25 Sep 2026)
  • A refund is final, and its amount starts at the unused part (decided 25 Sep 2026). freeze_refund() refuses any change to a refund row, its soft delete included; the screen pre-fills the unused sessions' (or days') share and the trainer may change it within what was paid.
  • collected_by is stamped, not chosen (decided 25 Sep 2026): stamp_payment_collector() writes it from client.client_type when the row is inserted — gym for a gym client, trainer for an independent one — and keeps it after, so a client whose type later changes keeps a true history. client.payment_mode is dropped: it could only ever say the same thing. payment_collector holds each side to its shape — a trainer row says how it was paid; a gym-desk row carries no method or reference, and is what the gym owes the trainer a share of.
  • Refunds (decided 25 Sep 2026): status refund and refunded_at. A pending request can still be written off by itself. CREATE VIEW payment_trainer_share WITH (security_invoker = true) AS   -- or it would read past the RLS policies
SELECT id AS payment_id, package_id, client_id, trainer_id, status, paid_at, refunded_at,
       round(cum * ratio, 2) - round((cum - signed) * ratio, 2) AS share          -- negative on a refund
FROM (
  SELECT y.id, y.package_id, y.client_id, y.trainer_id, y.status, y.paid_at, y.refunded_at, s.signed,
         sum(s.signed) OVER (PARTITION BY y.package_id ORDER BY coalesce(y.paid_at, y.refunded_at), y.id) AS cum,
         CASE WHEN k.trainer_share_percent IS NOT NULL THEN k.trainer_share_percent / 100
              WHEN k.trainer_share_amount  IS NOT NULL AND k.amount > 0 THEN k.trainer_share_amount / k.amount END AS ratio
  FROM   payment y JOIN package k ON k.id = y.package_id,
         LATERAL (SELECT CASE y.status WHEN 'refund' THEN -y.amount ELSE y.amount END AS signed) s
  WHERE  y.collected_by = 'gym' AND y.status IN ('paid', 'refund') AND y.deleted_at IS NULL
) x WHERE ratio IS NOT NULL;               -- one row per gym-desk payment with a share

CREATE FUNCTION check_package_ledger() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE total numeric; paid numeric; forgiven numeric; returned numeric;
BEGIN
  IF NEW.status NOT IN ('write_off', 'refund') OR NEW.deleted_at IS NOT NULL THEN RETURN NEW; END IF;
  SELECT amount INTO total FROM package WHERE id = NEW.package_id FOR UPDATE;   -- one ledger change at a time per package
  SELECT coalesce(sum(amount) FILTER (WHERE status = 'paid'), 0),
         coalesce(sum(amount) FILTER (WHERE status = 'write_off'), 0),
         coalesce(sum(amount) FILTER (WHERE status = 'refund'), 0)
    INTO paid, forgiven, returned
    FROM payment WHERE package_id = NEW.package_id AND deleted_at IS NULL AND id <> NEW.id;
  IF NEW.status = 'write_off' AND paid + forgiven + NEW.amount > total THEN
    RAISE EXCEPTION 'write-off of % exceeds what is still due on package % (%)', NEW.amount, NEW.package_id, total - paid - forgiven
      USING ERRCODE = 'check_violation';
  END IF;
  IF NEW.status = 'refund' AND (paid < total OR forgiven > 0) THEN
    RAISE EXCEPTION 'package % is not fully paid: only a fully paid package can be refunded', NEW.package_id
      USING ERRCODE = 'check_violation';
  END IF;
  IF NEW.status = 'refund' AND returned + NEW.amount > paid THEN
    RAISE EXCEPTION 'refund of % exceeds what was paid on package % (%)', NEW.amount, NEW.package_id, paid - returned
      USING ERRCODE = 'check_violation';
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER trg_payment_ledger BEFORE INSERT OR UPDATE OF status, amount, deleted_at
  ON payment FOR EACH ROW EXECUTE FUNCTION check_package_ledger();

-- the trainer's statement with one gym. Closed months carry the balance; this month is "so far" and owes nothing yet.
WITH months AS (                                   -- every month an arrangement covers, to this one
  SELECT a.gym_name, a.base_kind, a.base_amount, m::date AS month
  FROM   gym_arrangement a,
         generate_series(a.starts_month, coalesce(a.ends_month, :this_month), interval '1 month') m
  WHERE  a.trainer_id = :tid AND a.deleted_at IS NULL
), shares AS (                                     -- the trainer's share of what the desk collected, by month
  SELECT date_trunc('month', coalesce(paid_at, refunded_at) AT TIME ZONE :tz)::date AS month,
         sum(share) AS share,                          -- exact, refunds already negative
         count(DISTINCT client_id) FILTER (WHERE status = 'paid') AS clients
  FROM   payment_trainer_share WHERE trainer_id = :tid
  GROUP  BY 1
), owed AS (
  SELECT m.gym_name, m.month, m.month = :this_month AS so_far, coalesce(s.clients, 0) AS clients, coalesce(s.share, 0) AS share,
         CASE m.base_kind WHEN 'minimum' THEN greatest(m.base_amount, coalesce(s.share, 0))   -- the larger of the two
                          WHEN 'basic'   THEN m.base_amount + coalesce(s.share, 0)          -- basic pay + incentive
                          ELSE coalesce(s.share, 0) END AS owed
  FROM   months m LEFT JOIN shares s USING (month)
), filled AS (                                     -- what the gym paid, filling the oldest month first
  SELECT o.*, coalesce(r.total, 0) AS total,
         sum(o.owed) OVER (PARTITION BY o.gym_name ORDER BY o.month) - o.owed AS owed_before
  FROM   owed o LEFT JOIN (SELECT gym_name, sum(amount) AS total FROM trainer_payout
                           WHERE trainer_id = :tid AND deleted_at IS NULL GROUP BY 1) r USING (gym_name)
)
SELECT month, so_far, clients, share, owed,
       least(owed, greatest(0, total - owed_before)) AS paid,              -- on this month: paid in advance, if anything
       CASE WHEN so_far THEN NULL                                          -- not due until the month ends
            ELSE owed - least(owed, greatest(0, total - owed_before)) END AS balance
FROM   filled ORDER BY month;                    -- balance due = the sum of the balance column
