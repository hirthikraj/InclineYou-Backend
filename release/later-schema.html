Conventions that hold on every table
primary-key
Every table has id uuid PRIMARY KEY DEFAULT gen_random_uuid(). Ids are normally generated client-side (UUID v4); the default is a fallback.
ownership
Trainer-scoped tables carry trainer_id and every query filters on it, so a wrong id answers 404, not 403.
soft-delete
deleted_at NULL means alive. Nothing is hard-deleted; every read filters deleted_at IS NULL. Log tables (otp_request, client_assignment, team_activity) have no deleted_at — a mistake is corrected by writing another row. Since V21 the request role holds no DELETE except on attention_dismissal, web_session and otp_request, and no UPDATE on the three logs.
erasure
Deleting an account is an erasure (P2), not a soft delete. erase_account() sets the personal columns of app_user, trainer and client to NULL under a CHECK that lists them, and deletes the trainer's trainer_business row and each erased client's client_schedule row with its slots, which are personal from end to end, so the rows stay as tombstones, and the phone number is released. It also deletes the person's web_session rows and empties billing_event.payload on their subscription; otp_request rows age out on their own 30 days, never early, because a running lock is an abuse control. A trainer deleting one client is the same erasure at client scale: erase_client(id), granted to the request role and refused unless the caller coaches that client, runs erase_clients() and writes an erasure_log row of kind client; the ledger stays as a nameless former client. purge_tenant() is the one hard delete: it empties a closed workspace once purge_after has passed. What survives is erasure_log, which holds counts only, and nameless amounts and dates in workspaces the person did not own.
updated-at
updated_at is maintained by the set_updated_at() trigger on every table that has it, and is the sync cursor. Since V21 there is no exception: working_hours, time_block and batch used to take the device's own value on sync push, which a wrong clock turned into an edit no other device ever pulled.
tenant-id
tenant_id is the workspace a row belongs to. It is stamped on insert by stamp_tenant_id(), refused any change by freeze_tenant_id(), and row-level security filters on it.
money
Money is numeric(10,2), percentages numeric(5,2). One currency per workspace: tenant.currency (ISO 4217, default INR) is the only currency that workspace's money rows may carry. Each one has a composite foreign key (tenant_id, currency) → tenant(id, currency), so no SUM ever adds two currencies, and a workspace's currency cannot change once a money row points at it. Only currencies with at most two decimal places are offered (Currency.getDefaultFractionDigits() ≤ 2, checked in code); the three-decimal Kuwaiti and Bahraini dinars and the Omani rial are refused rather than rounded. The one exception is subscription, whose price and currency come from its plan_price row — the price of the trainer's billing region — not from a workspace.
phone
Every phone column is E.164 (+919841022119), varchar(16), under the same format CHECK: + and 7–15 digits, and a +91 number must still be a ten-digit Indian mobile. One column, never a country code and a number split in two. Parsing, validation and display go through libphonenumber on the backend and the web; a number typed without + is read in the region of the workspace's tenant.country. The display grouping and the wa.me link (the digits after +) are derived, never stored.
time
An instant is timestamptz, always UTC. A date or a wall-clock time is a calendar day or a time in the trainer's timezone (trainer.timezone, IANA), never the server's and never the client's — one diary has one clock. client.timezone only converts what the client is shown.
enumerations
Enumerated columns are plain varchar, never a Postgres ENUM. Vocabularies (profile lists, nudge kinds, payment.method) are validated in application code; since V21 state machines and money columns also carry a CHECK, so a new state is a code change plus one DROP / ADD CONSTRAINT in a migration. Legal values are listed per column under allowedValues.
foreign-keys
Unless stated otherwise a foreign key is ON UPDATE NO ACTION, ON DELETE NO ACTION — rows are soft-deleted, so nothing cascades.

Deferred in the v1 review

What the review of the agreed schema set aside for a later release, beyond the tables below — so it can be picked up without re-reading the whole conversation. Each item is additive to bring back.

Money book

  • Client bills — invoice_counter, payment.invoice_no, payment.invoiced_at, freeze_invoiced_payment(), the payment_invoice check, uq_payment_invoice_no and POST /v1/payments/{id}/invoice. Not tax invoices; additive to bring back, numbered from 0001. The web's invoice screens are hidden (MUST-19). Not MUST-18, InclineYou's own GST invoice to trainers, which stays in v1.
  • payment.receipt_no — held, as before the review (below).
  • Clients outside India — trainer_business.payment_link and a payment_link method on payment. InclineYou is India-only for now. The international work already on the agreed page (E.164 phones, one currency per workspace, priced by region) stays as defaults and needs no change to switch on.

Reminders

  • trainer_notification — the trainer's bell. Nothing writes it without the portal, teams or gyms; it returns with the portal.
  • Automated and portal channels — nudge_log.channel already allows whatsapp_auto (WhatsApp Business API, v2) and portal; v1 writes only whatsapp_manual. Still to design when they ship: a delivery-events table for delivered / read / failed (so nudge_log stays append-only), and the per-message channel setting, most likely a column on nudge_template.

Client portal

  • The portal's row-level security policies were dropped from the agreed tables and return with it: the client read on scheduled_session (scheduled_session_client), on set_log, and on templates / assessment_template.
  • Columns kept on agreed tables but unused until then, marked Client portal · next release there: client (activity_level, timezone, membership_status and its dates), client_note.shared_with_client, and who logged a session (logged_by, held when workout_session merged into scheduled_session).

Diary

  • scheduled_session: series_id, cancelled_by, moved_from_at, client_confirmed_at, batch_id — with time_block and batch.
