API contract, screen by screen

What each web screen loads and what each of its actions calls, written against the 41 tables approved in proposed-schema.html — not against the old REST, which describes the pre-v1 schema. The UI of record is the MockUI (InclineYou-MockUI/mock-ui/web, served on localhost:3100); where it and web app/web differ, the MockUI wins. Its fake backend (mock/router.ts) shows what each screen does, but it still speaks the old wire, so the shapes below are redesigned for v1 rather than copied from it. Where the frontend wants something the schema does not hold, it is listed under Schema review for a decision rather than quietly patched on either side. Once this settles it replaces the relevant parts of backend/API.md.

Sign in & setup

/sign-in · /sign-in/verify · /sign-in/new · /sign-in/consent · /setup/* 7 endpoints · setup reuses 4

Phone + a 6-digit code over WhatsApp only, no SMS (decided 24 Sep). The MockUI flow: number (/sign-in) → code (/sign-in/verify, with a resend countdown and live delivery status) → one of: an existing trainer goes to /today, or to /setup if onboarding isn't finished, or to /sign-in/consent if the privacy notice has changed since they accepted it · a new number goes to /sign-in/new (accept the notice, become a trainer) → /setup (eight steps) → /today. The number rides in a cookie, never in a URL. Google sign-in is out of v1 (GOOGLE_SIGN_IN_ENABLED = false).

POST/v1/auth/otp/requestSend a sign-in code on WhatsAppsame 
{ "phone": "+919841022119" }   →  204

Writes an otp_request (purpose = sign_in, the code hashed) and hands it to WhatsApp, storing provider_message_id. The same answer comes back whether or not the number has an account, so the endpoint can't be used to find out who's signed up.

Errors

Schema review — Sign in & setup

R60 · decided 26 Sep
What happens when a client's number signs in on v1?

The MockUI routes client, invited, removed, paused and unattached numbers into the portal (/me/today, /invite/…, and walls), and the portal is next release. A trainer who is also somebody's client has a mode switch in the rail.

Decided: in v1 the backend answers verify for a number that is only a client with 403 PORTAL_NOT_IN_V1 and opens no session. Next shows a single screen: "Client sign-in opens soon. Your trainer will share it." A number that is both a trainer and a client signs in as the trainer, and the mode switch is hidden. All portal routes stay built behind RELEASE.

R61 · decided 26 Sep
How long does a web session last?

web_session.expires_at is stored, but no rule for it has been written down.

Decided: 30 days after last use, sliding. Each request moves expires_at out, at most once an hour, to spare the write. A trainer at the same gym desktop every day never gets signed out, and one who stops for a month signs in again. Devices can be revoked from Settings.

R62 · frontend (launch blocker)
Send X-InclineYou-Client: web.

The MockUI sends no client header, so today it would get the phone's 7-day, unrevocable JWT, which is the WEB_LAUNCH.md blocker. Every web request, and verify above all, sends the header. Then revocation, sign-out-everywhere and the devices list actually work.

R63 · frontend
Setup stops using the sync protocol.

lib/setup/api.ts reads with /v1/sync/pull and writes hours and packs with /v1/sync/push. Both become the REST calls in the table above. With that, nothing on the web speaks sync.

Today

/today 10 reads · 9 actions

One route, four states chosen by the data rather than the URL: a session running, one started but never opened, the day over (tomorrow's first), and no clients (first run). Sections: the hero (up to three cards), the day ribbon (sessions, gaps, working windows), the attention queue, the week card, the money card, recent activity and the ⌘K palette. Refreshed every five minutes and after every write.

What changes from the current build

  • 10 reads + 1 conditional → 9 parallel reads, none conditional. The live set count rides on the session row, so there's no second round.
  • The two unbounded reads are gone. GET /v1/workouts (the whole history, used only for "last session" and "100th session") becomes two per-client aggregates on the client summary. GET /v1/payments (every payment ever, used for "owed") becomes amountDue on the package plus a month summary.
  • There is no workout_session in v1. A session's log is the scheduled_session row itself (started_at / ended_at). So running, open log and late are all read off session rows.
  • Three writes move to the server: renew copies the package terms itself, marking done is one batch request (no browser loop guarding the pack count), and closing a log no longer reads before it writes.

Schema review — where Today and the approved schema disagree

In every case below, the recommendation is to adapt the frontend and leave the schema as approved. None of these needs a V2 migration. R3 and R4 were decided on 26 Sep 2026; R5 is still open.

R1 · frontend
Dismissals have no id.

The key is (trainer_id, client_id, kind). The UI's dismissalId (for Undo and Restore) becomes clientId + kind.

Keep the schema. A composite key is the correct shape: one silence per client per kind.

R2 · frontend
No workout_session: the log is the session.

RunningSession.workoutId, openLogs and every /sessions/{workoutId} link switch to the scheduled session id. programId + templateDay becomes workout {id, week, day}.

Keep the schema. It removes a whole id space from the UI.

R3 · decided 26 Sep
The trainer's share is set per package, not per trainer.

On a gym package the trainer's cut depends on the package amount and isn't a fixed rate, so trainer_share_percent | trainer_share_amount on each package is correct, and trainer.gym_share_percent stays gone. The frontend adapts:

  • The per-session rate is the client's newest package: amount / sessionsTotal × the trainer's share (trainerSharePercent, or trainerShareAmount / sessionsTotal). A package with no share is 100% the trainer's.
  • The day's "your ₹" adds up each session's own rate, so a floor client and a home-visit client on the same day are valued differently.
  • A free gap has no package, so its worth shows gross, labelled "gross", or is hidden. It no longer applies a trainer-wide percentage.
  • TodayData.trainer.gymSharePercent and RateSource.gymSharePercent are removed, and the money card reads gymCut / yours from L6.
R4 · decided 26 Sep
"Billed this month" means packages sold.

Billed = packages started this month, collected = payments paid this month, pending = everything still owed right now. L6 is written that way. The frontend drops its payment-sum version of DeckMoney and reads L6 instead.

R5 · decided 26 Sep
Renew uses the pack's current price.

When package.pack_id points at a pack that is still active, renew takes that pack's current amount, sessions, validity_days and trainer share. When the pack is inactive, deleted or null (a custom package), it repeats the old package's terms. The server does this; the frontend sends nothing but the package id.

R6 · frontend
home_visit is a third delivery mode.

The UI's DeliveryMode is floor | remote. The schema allows floor | home_visit | remote on client_schedule, slot and session. The ribbon needs a third tone and the filter chips a third option.

R7 · frontend
"Has a note" reads the pinned note, not the goal.

v1 has client_note with pinned. The chip = session.notes is non-empty OR client.hasPinnedNote. client.goal stops feeding it. It's still a boolean that never looks at what the note says.

R32 · frontend
Currency comes from /v1/me.workspace.currency.

The MockUI already formats money through useMoney() from the workspace's currency; it just reads it from GET /v1/tenant. That read moves onto /v1/me, and lib/tenant/api.ts takes it from there.

R8 · frontend
The day boundary comes from the workspace's time zone (R55).

The frontend computes startOfDay(now) on the Next server, whose zone isn't the trainer's. L4 takes dates and resolves them server-side, and the frontend formats times with /v1/me.workspace.timezone.

R9 · frontend
Payment statuses.

confirmed is gone: collected = paid. The new states write_off and refund count as not owed.

R31 · decided 26 Sep
Can the two new bands be snoozed? The schema says no.

The check constraint attention_dismissal_band allows only kinds pack · overdue · missed · quiet · no-program · unmarked · milestone · log, so Not now on an assessment-due or pause-due row would be refused by the database.

Decided: no Not now / Not again on these two, and no schema change. Both clear themselves when acted on: take or reschedule the assessment, or resume or extend the pause. "Not now" on either would really mean "change the date", which the row should send you to do. The alternative is a V2 migration that adds assess and pause to the check.

R10 · backend, later
An index for the per-client aggregates, if L3 gets slow.

sessionsDone / lastDoneAt use idx_scheduled_session_client. If a long-tenure roster makes L3 slow, a partial index (client_id, scheduled_at) WHERE status = 'done' is the fix. That would be an additive V2, so it's not proposed now.

R21 · decided 26 Sep
How far ahead do weekly slots book sessions?

Schema review — Programs

R45 · decided 26 Sep — V2 migration
Is Monday always Day 1? The MockUI says yes, and the schema can't store it.

The MockUI keeps a templateDay on each weekly slot (add-client step 3 and the Assign panel both send {day, weekday, time}), and every booking from a slot gets that day's workout. client_schedule_slot has weekday and start_time but no program day, so the v1 schema can only give each booking the next workout in sequence.

The two only differ when something breaks the pattern. Say a Monday session is cancelled. Fixed day: Wednesday is still Day 2, and Day 1 is skipped that week. Sequence: Wednesday becomes Day 1, and every later booking shifts by one, which means re-linking up to 4 weeks of pre-booked sessions on every cancel.

Decided: fixed day, with a small additive V2 migration (not yet written): client_schedule_slot.program_day smallint NULL (1..7, checked against the program at write time). It matches the MockUI and how trainers talk ("Monday is legs"), keeps pre-booked sessions stable, and makes the week counter simple. Null keeps the sequence behaviour for a client with no program. This revises R22: step 3 keeps sending day.

R46 · backend
A tree save diffs by id, and refuses a stale save.

A delete-and-reinsert save would orphan every booked session's workout_id. Diffing keeps them linked. If-Match: revisedAt means the builder's autosave in one tab can't silently undo edits from another; the save gets 412 and the builder reloads.

R47 · frontend
Hide "Tell the client".

postPlanNotice writes to the portal bell, which is out of v1. Put it behind RELEASE like sendAssessments.

R48 · frontend
Exercise names come with the program.

lib/programs/api.ts stops calling /v1/exercises?ids= and reads L3's exercises dictionary. lib/sessions/api.ts does the same with the log's embedded names.

R49 · frontend
An exercise has a logType, not default kinds.

exercise.log_type is weight_reps | reps. An exercise added mid-session gets weight × reps or bodyweight × reps from it. Everything richer comes from a plan's sets. The defaultLoadKind/defaultEffortKind in Log session L3 were a draft and are corrected to logType.

As the MockUI does: assigning a new template completes the current plan. The Assign panel should say so when the client has one ("Replaces Strength base, week 5 of 8").

R51 · decided 26 Sep
Two v1 tables have no screen: gym_arrangement and trainer_payout.

The approved schema defines what the gym owes a trainer as "a monthly statement over gym_arrangement and these rows": a base fee (minimum or basic) and the payouts the gym actually made. The MockUI's Gym share page only shows the split on each payment. There's no way to say "the gym pays me ₹15,000 minimum" or "they transferred ₹22,000 on the 5th", so nothing ever writes either table.

Decided: add a small settlement card to Gym share in v1 (A2). The page would read "Owed by the gym this month: ₹X (your share of gym-collected money, or the minimum if higher) · received ₹Y · balance ₹Z", with two actions: set the arrangement and record a payout received (GET/PUT /v1/gym-arrangement, POST /v1/trainer-payouts). Most trainers today are paid by a gym that isn't on InclineYou, and "has the gym paid me" is the question this page exists to answer. The alternative is leaving both tables idle until the next release. That's harmless for the schema but leaves the most common arrangement half-tracked.

/settings · /settings/nudges · /settings/profile[/certifications|experience|specialities|languages|work|social] 4 reads · 10 actions

Two strips. Settings is what only the trainer sees: Account (you, signing in, where you do business, delete) and Nudge messages. Your profile is what a client reads, reached from the account menu, in seven tabs: identity · certifications · experience · specialities · languages · work & hours · social. Each tab saves only its own fields. /settings/hours redirects to the work tab. Out of scope here: the Plan tab (subscription and trial, MUST-16), which will be covered with billing later.

What changes from the current build

  • Very little. These screens already speak a PATCH /v1/trainers/me where absent means untouched. The work is mapping its fields onto trainer + trainer_business + app_user.
  • The working week stops going through the sync envelope. The MockUI saves each changed weekday with /v1/sync/push. It gets its own PUT.
  • Weekdays are 1–7 (Monday = 1), as in the schema. The MockUI's profile code uses 0–6.

Schema review — Settings

R55 · decided 26 Sep
One clock or two? trainer.timezone and tenant.timezone both exist.

The MockUI's Account tab shows the workspace's time zone ("your diary runs on this clock"), next to its country and currency. Earlier sections of this contract read the day boundary from trainer.timezone.

Decided: the workspace's time zone for everything in v1: the day boundary, booking, Today and the money months. A workspace's books have to close on one calendar. trainer.timezone stays unused until a coach who travels needs a personal display clock. If you agree, /v1/me returns workspace.timezone and conventions and R8 change to match.

R56 · frontend
Weekdays 1–7.

lib/profile/api.ts filters weekday 0–6. The schema and every other screen in this contract use 1 = Monday … 7 = Sunday.

R57 · frontend
The working week saves through PUT /v1/working-hours.

saveWorkingHours stops pushing working_hours rows through /v1/sync/push, the one write left on the web that used the phone's protocol. The dirty-days-only rule moves into the request body.

R58 · frontend
Hide the notification bell in v1.

The top bar's bell reads /v1/notifications, whose three kinds (a client paid, cancelled, or entered a reading) all come from the client portal. There's no v1 table behind it (client_notification is in later-schema.html), so in v1 it would always be empty. Put it behind RELEASE.

R59 · frontend
Consent lives on the person, not the trainer.

privacy_policy_version / privacy_accepted_at are on app_user (a pair, app_user_privacy_pair). /v1/trainers/me returns both, and acceptPrivacyPolicy writes both. This is invisible to the MockUI; noted so the backend doesn't add a trainer column.
